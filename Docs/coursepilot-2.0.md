# CoursePilot 2.0 产品设计文档

## 1. 背景与定位

CoursePilot 1.0 是一个多 Agent 架构的课程问答平台：用户打开 Web、选定课程，在 learn / practice / exam 三种模式下与系统交互，每次交互都是被动响应。到 2026 年，这种"你问我答"的形态已经无法与通用 Chat 产品和 NotebookLM 等专业工具拉开差距。

2.0 的定位是：**有状态的 AI 课程私教**。核心转变有两个：

- **状态中心化**：所有功能围绕一份持续演化的「学习档案」（概念目录 + 掌握度 + 错题 + 计划，可选 Wiki）读写，而不是各功能各管各的。
- **主动化**：Agent 不再只等用户来问，而是按计划推任务、推小测、推周报，学习行为由系统驱动。

一句话概括：**学习档案是大脑，计划是心跳，IM 是触手，相机是眼睛；Wiki 是可选的知识视图。**

### 1.1 竞争差异化

| 竞品 | 能力 | 缺失 |
| --- | --- | --- |
| NotebookLM | 从资料生成 study guide、闪卡、quiz、播客 | 无掌握度状态，不知道用户学得怎么样 |
| Gauth / Photomath | 拍照解题，步骤讲解 | 无课程上下文，每次解题都是孤立事件 |
| ChatGPT Scheduled Tasks | 通用定时任务 | 与学习内容、掌握度无联动 |
| 各类 IM 学习 bot | 推题、提醒 | 玩具级，无持续学习状态 |

单点功能均已有成熟产品，2.0 的护城河是**闭环**：每个输入（提问、错题、小测、拍照）都更新系统对用户的理解，每个输出（讲解、推送、计划）都基于这份理解。目前没有产品做全这条链路。

## 2. 与 1.0 的取舍

| 类别 | 内容 |
| --- | --- |
| 砍掉 | 多 Agent 编排（Router / Tutor / QuizMaster / Grader）；learn / practice / exam 三模式的硬性划分；整卷生成方向 |
| 升级 | 每次请求传课程参数 → 默认通用会话自动解析课程、也可进入固定课程工作区；纯 RAG → RAG + 可选 LLM Wiki；被动问答 → 计划驱动；单一 Web 入口 → Web 为主、IM 为辅 |
| 保留 | 教材解析与索引管线；出题与评分能力（合并为 `practice` skill）；把 1.0 ToolHub 的权限、预算、幂等与审计要求作为回归清单，但不复用其简陋实现；benchmark / judge / review 评测资产 |

2.0 是有意的上层重建，不向最终用户长期并行提供两套产品形态；工程迁移期保留 1.0 baseline 和特性开关，新链路通过回归门槛后再退役旧实现。

## 3. 核心功能模块

### 3.1 Super Agent 与课程工作区

以单一强 Agent 取代 1.0 的四角色编排。通用讲解、学习规划和图片内容确认都是 Super Agent 的默认能力：系统提示词固定要求先查课程证据、引用页码、证据不足时明说；规划遵循固定 schema；图片先展示转录并处理不确定项。只有练习和 Wiki 维护这类具有独立长流程与专用产物的能力以 skill 按需激活。

- **通用模式默认开启**：Web 与 IM 渠道默认创建通用会话。Agent 根据用户明确提及、问题内容、材料引用和近期上下文解析相关课程；无法可靠确定时先询问，不跨课程猜测取证。
- **课程工作区仍然保留**：Web 左栏可进入某门固定课程；课程会话整个生命周期内固定 `course_id`，类似 Claude Code 会话绑定目录。切换工作区只新建或续接目标会话，不修改旧会话归属。
- **会话列表可辨认课程**：会话标题旁显示课程稳定色点。课程会话使用固定课程色；通用会话根据最近一次可靠解析显示色点并保留通用标记；尚未解析时使用中性灰。
- **意图驱动的交互**：不再要求用户预先选择 learn / practice / exam。"给我出几道题"激活练习 skill，"讲讲这个概念"由 Agent 直接讲解。
- **练习是一个完整 skill**：出题、接收作答、评分、讲评、归因和变式题均属于同一个 `practice` skill，不再拆成 QuizMaster / Grader 两个角色。
- **用户可导入 Skill**：管理页支持上传单个 `SKILL.md` 或受限 zip，预览权限后按全局/课程启用。首版只允许 prompt-only Skill，不执行脚本、不安装依赖，也不能自行增加工具权限。
- **规划是内建能力**：Agent 可直接读取和修改当前课程计划，`plan_v1` schema、版本校验与调度服务负责保证结构正确、只改未来条目，避免把产品主循环包装成额外 skill。
- **图片点评不是 OCR skill**：附件先由视觉接入层产出结构化转录，主 Agent 负责展示转录、确认歧义和讲解；如果图片是练习作答，再激活 `practice` 完成评分。
- **会话列表与持久会话**：前端始终展示完整会话列表，以课程色点和通用图标区分 scope；历史会话可回看、可续接，取代 1.0 用完即弃的对话形态。
- **有记忆的开场**：新会话开始时根据所绑定课程主动续接——"上次学到 5.3 节，链式法则那道题还没弄懂，继续吗"。

### 3.2 知识仓库：RAG + 可选 LLM Wiki

“知识仓库”是统一用户入口，RAG 资料库与 Wiki 知识页是两个主要组成部分，不用 Wiki 的名字代指整个知识层：

- **RAG 资料库（证据层）**：默认主视图，完整保留 1.0 的上传、文本解析、切块、嵌入、索引、混合检索、页码引用和检索验证能力。
- **Course Wiki（可选理解层）**：默认关闭。用户在课程管理页开启后，可对某本教材点击“解析到 Wiki”，再生成概念页、公式页和章节页；失败不影响 RAG。

RAG 建索引后总会生成供归因使用的稳定概念目录，但不会自动生成 Wiki 页面。Wiki 开启后才持续演化：只在用户显式触发教材解析、经用户确认的纠错，或用户明确要求整理时更新正文。提问、错题和小测主要写入证据事件；页面中的掌握度由状态层读时渲染（见 3.7），不由 LLM 写入 Markdown。

Wiki 页面为人类可读的 Markdown，以 **git 存储**，天然具备版本历史、diff 与回滚。它具备**可提示性**——可直接作为 Agent 上下文注入，也允许用户查看和编辑。这是它相对 RAG 检索碎片的核心优势：系统化、结构化、可解释。

二期可选：**Deep Research 补料**。教材讲不清的概念，Agent 联网检索更好的讲解与例题，筛选后沉淀进对应 wiki 页。

### 3.3 计划与定时任务

- **长期计划**：输入考试日期与范围，生成整个复习周期的计划（每天学什么、练什么）。
- **动态重排**：根据连续答错、FSRS 到期、计划进度偏离等可解释信号建议调整后续计划；复合掌握度分数只展示和排序，不直接触发重排。真正改动仍只影响未来条目并遵循确认规则。
- **定时任务**：计划落地为定时触发的动作——早晨推今日任务、晚间推小测、每周日推学习周报（本周掌握度变化 + 下周建议）。
- **考前冲刺模式**：距考试 N 天自动切换策略，按掌握度集中攻弱项。
- **错题间隔重复**：错题自动生成同考点变式题，按 FSRS 排入复习队列（见 3.7）。

设计原则：主动性必须挂在明确目标（考试、计划）上，不做泛化的"猜你想看"式推送。ChatGPT Pulse 的下线证明了泛化主动推送不成立，而目标绑定的定时任务是被验证的形态。

### 3.4 即时通讯渠道

首版只接入一个 **IM 渠道**，其余渠道保留统一接口，后续按 adapter 增加。

- **定位**：IM 是辅助渠道——承接主动推送和碎片化提问；系统化学习（看 wiki、管理计划、上传教材）仍在 Web 端完成。
- **下行（推）**：每日任务、小测、错题提醒、周报，使用 IM 文本或消息卡片。
- **上行（问）**：文字提问、拍照提问，与 Web 端共享同一个 Agent 与同一份学习档案。首版不做语音输入。
- **IM 会话规则**：每个用户只有一个通用 IM 会话，不提供课程选择控件；用户通过自然语言说明课程，或由系统根据问题解析相关课程。
- **推送治理**：频率上限、免打扰时段、可退订，作为渠道层的基础约束。

### 3.5 OCR 多模态输入

- **拍题提问**：用户拍照上传遇到的题目，先由具备视觉能力的模型转录题干、公式与图形，再由主 Agent 结合当前课程证据讲解。文本主模型与视觉模型可来自不同 provider。
- **拍答案点评**：用户上传自己的手写解答，系统先展示结构化转录，再逐步点评哪步对、哪步错、错在哪个概念。低置信度或关键公式存在歧义时，先请用户确认，不写入证据事件。

与 Gauth / Photomath 的差异：它们是无状态解题器，CoursePilot 的 OCR 输入会进入学习档案，成为掌握度判断与计划调整的信号。

### 3.6 记忆与上下文

- **学习档案为统一记忆载体**：用户画像、掌握度、错题、计划进度收敛到一处，取代 1.0 中分散的会话状态与情景记忆。
- **按解析后的课程上下文组装**：课程会话使用固定课程；通用会话每轮先得到受控的课程解析结果，再只从该范围组装 Wiki、RAG 证据、近期错题和计划状态，而不是无差别跨课程检索。
- **跨渠道一致**：Web 与 IM 共享记忆，换渠道无缝续接。

### 3.7 掌握度模型

掌握度是整个闭环的中心数据，设计原则：**LLM 只做归因，数值更新用确定性算法**，杜绝模型幻觉直接污染学习档案。

- **LLM 职责边界**：把一次交互解析为结构化证据事件——关联概念 + 事件类型（答对 / 答错 / 追问 / 用户标记），不输出任何数值。其中只有可判定的客观作答证据直接驱动 BKT / FSRS，追问和自述保留为辅助信号。
- **状态层**：每个概念维护掌握概率 P 与记忆稳定性 S。P 用经典 BKT（四参数、固定默认参数的最简实现）按证据事件更新；S 用 FSRS 半衰期模型刻画遗忘。当前掌握度 = BKT 后验 × 时间衰减。
- **复习调度**：弱概念与错题按 FSRS 排期进入复习队列，不自行发明排期算法。
- **置信度**：证据不足的概念显示"数据不足"，不给出强弱判断，避免冷启动误判。
- **用户纠偏**：一键"我已掌握 / 我还不会"，作为显式用户标记事件入流并在 UI 单独展示，不伪造成多次客观作答。
- **事件溯源**：掌握度不存不可解释的最终值，存 append-only 的证据事件流，当前值由重放计算。纠错通过 correction / supersede 新事件完成，不物理删除历史；由此获得可回退、可审计和可评测。

## 4. 模块联动（闭环）

```
拍照 / 提问 / 小测 ──→ 证据事件 ──→ 掌握度更新、必要时 Wiki 更新 ──→ 计划动态重排
                                                              │
      用户 ←── IM 推送（每日任务 / 小测 / 周报）←── 定时任务 ←──┘
```

任何单个模块被替代都不影响整体价值成立；反过来，缺了学习档案这个中心，各模块就退化为市面已有产品的复制品。

## 5. 部署形态

主形态为**前端 + 后端本地部署**：Web 前端与后端运行在同一台机器，IM 渠道作为辅助入口接入本地后端。本地形态下定时任务在停机期间不执行，采用"下次启动时补投当日任务"的降级策略。

演进方向为后端服务器化，获得可靠的定时推送。为此核心保持 headless：渠道层（Web / IM，其他仅协议）与核心解耦，服务器化时只迁移后端，不改动核心逻辑。

## 6. 评测与可观测性

- **全链路 trace 打点**：每轮对话、每次 skill 调用、每次档案写入记录一个 span（JSONL 落盘），包含输入、输出、引用证据、token 消耗。
- **离线采样评测**：定期用 LLM-as-judge 对 trace 抽样评分——讲解是否忠于教材、概念归因是否正确、推送是否恰当。
- **事件流回放**：掌握度算法变更后，用历史证据事件流重放对比新旧掌握度曲线，作为"不退化"的验证手段。
- **冒烟 benchmark**：保留一小组核心场景用例，用于发版回归。

## 7. 分期规划

| 阶段 | 内容 | 说明 |
| --- | --- | --- |
| Phase 1 地基 | Super Agent、通用/课程双会话、Course Resolver、知识仓库中的 RAG + 概念目录、`practice` skill、会话列表、掌握度与 trace | 一切下游功能的数据基础，先在 Web 端跑通 |
| Phase 1.5 可选 Wiki | 课程开关、按教材解析、预览与回滚 | 默认关闭，独立验证，不阻塞 RAG 主线 |
| Phase 2 主动化 | 长期计划、单 tick 调度、隐藏系统会话、IM 渠道 | 四者一体，首版不接其他 IM |
| Phase 3 多模态 | OCR 拍题 / 拍答案点评 | 相对独立，不阻塞主线 |

排序理由：概念目录与掌握度是所有下游功能的数据基础；Wiki 属于可选增强；IM 推送没有计划就没有内容可推；OCR 没有学习档案就退化为解题器。

## 8. 非目标

- 播客 / 音频生成（NotebookLM 已做到很好）
- 通用闪卡产品化（红海；闪卡仅作为间隔重复的内部载体）
- 泛化每日简报（已被 ChatGPT Pulse 证伪）
- 整卷生成与仿真考试
- 社交 / 对战 / 班级模式（偏离单人私教定位）
- 服务器多租户 / 商业化运营能力（当前为单用户本地形态）
- 通用会话在同一轮无边界地跨多课程读写；若无法解析唯一课程，必须先询问用户
- 首版 Telegram、微信等额外渠道，以及语音 / ASR 输入
